# Bethke — Game Development and Production (2003) — lossless notes
Author: Erik Bethke (producer of Starfleet Command, founder of Taldren). Foreword by BioWare founders Zeschuk & Muzyka. 4 parts: I intro, II how to make a game, III game development (deep dive), IV outsourcing/resource guide. Core thesis: GAME DEVELOPMENT IS SOFTWARE DEVELOPMENT — formal methods (Unified Process, UML, Gantt/PERT) apply; "games are art not science" is a false rationalization.

## Ch1-2 Overview & Why Make Games
- Book = production methodology: plan first (requirements capture via UML use cases), task visibility, controlling feature creep, alpha/freeze, shipping (bug triage, beta program), post-release (patches, expansions, user extensibility — plan it in the ARCHITECTURE stage, not at the end; Doom/Quake coined "level designer"; Total Annihilation's greatest strength = designed for user modification). Fan message boards = critical to long-term success.
- Mega-hits (Doom, Warcraft, Myst, Gran Turismo, Mario64, The Sims): feature set is SMALL but polished to a superior degree. Solo teams need the discipline MORE, not less.
- Success = a long race of many game projects, not a sprint to fast cash. Know why you're making THIS game and where it fits in a chain of projects.
- Games teach (peek-a-boo/hide-and-seek = hunting/evasion training; Royal Game of Ur 2500 BC; Go used by Emperor Shun to train his son; chess). Game genres mirror source material: gambling/parlor/puzzle, military & sports simulations, RPGs. Games = the most interactive medium: the player is the hero; only in a game can you try actions, see outcomes, explore a model of a world.

## Ch2 (end) + Ch3 What Makes Game Development Hard
- Starfleet Command origin: Star Fleet Battles board game (32 "impulses" per turn ≈ proto-real-time); "real-time tactical" career in 8 empires; prestige points economy. RPG lineage: campfire → D&D (Gygax; cooperative not competitive; player-written backstory) → Zork/King's Quest → Bard's Tale/Ultima/Wizardry → 1997 comeback trio: Baldur's Gate, Diablo (tight UI + online hack), Ultima Online (first viable MMO; Bethke paid $10/mo to mine virtual ore). Money note: "focus on making a great game; the money will come" — honesty/truth/clarity matter because only ruthless pursuit of a CLEAN TIGHT GAME makes greatness.
- Economics (2001 PC): 3,000 titles/yr released; ~100 profitable; top 50 make real money. Deal shape: $1-3M advance over 12-36 months; marketing $250k-1.5M; royalty 10-30% (typ 15%); retail $35 → wholesale $21. BREAK-EVEN ≈ 500,000 UNITS (at 15% royalty against $1.5M advance; royalty check $75k arrives 9-18 months post-release). Royalties will NOT feed the team; promises of royalties as salary offsets → disenfranchised employees. Even good games undersell: Hexen II ~30k, Messiah <10k in 90 days, Fallout 1 ~120k year one; most sales come in the FIRST 90 DAYS. SFC1 350k year one; SFC2 120k in 6 months; Diablo II 2M orders day one (> Interplay's market cap).
- Scope must match financial parameters: "when it's done" is only for Blizzard/BioWare/id capital; everyone else: find the BEST game within the budget. id once made games for $6/hr at SoftDisk; Blizzard was once a contractor for Interplay. Steppingstones, not one ambitious leap.
- Two unprofitable attitudes: FEATURE STORM ("MMO + magic + martial arts + vehicles + starships" — every feature you ship creates an expectation you must FULLY deliver; Warcraft tight about orcs+resources, Quake tight about FPS; unmet hype gets crushed) and WHO-CARES ("just a little spades game" — if worth doing, worth doing excellently; weak demo = proof you're weak). Counter-example: Silver Creek's Hardwood Spades — 3 devs, best spades ever, direct sales, no advance, brand built step-by-step from Hardwood Solitaire 1997.
- Long projects table: Stonekeep 5yr weak; Daikatana 4yr overruns weak; Messiah 5yr weak; Max Payne 5yr; The Sims 5yr AMAZING (unique: 5 years with zero competitors for the underserved women's market + EA sales muscle; Will Wright experimented 10+ years, ~10 sim games, only SimCity + The Sims hit); Baldur's Gate 3+yr strong (right time + AD&D license, ~4M units w/ expansions); Duke Nukem Forever unreleased; Stonekeep 2 & UO2 CANCELED after millions + magazine covers. Late games → publisher cash-flow stress → publish MORE titles → less attention each → ship early → vicious cycle.
- SFC project reality: inherited late; fixed date (summer '99) + granted resources → flexible features/fixed timeline; coded until 2 weeks from master, patched through manufacturing; shipped with known bugs, patched fast; 350k units. Lessons: constraints = focus ("no budget for movies → random mission/campaign generator with story missions embedded like raisins in pudding"); complex games (SFC, RPGs) inherently need MORE/different QA than tight shooters — treating all games identically in QA is wrong.
- PREPRODUCTION thesis: civil engineering works because process; software slips because process immaturity (McConnell, After the Gold Rush). True preproduction = requirements distillation → analysis → culling to business parameters → detailed game/art/audio/tech designs → ANOTHER feature-culling revision → risk callouts + alternatives → present to all stakeholders. Bethke wants 25-40% of prerelease time in preproduction; during production there should be FEW surprises (8-hour days, vacations, school pickups). Industry compresses preproduction because no hype/honor in it. His dream economics: launch 4,000-5,000 projects, give each 2-9 months preproduction, CANCEL most, produce only top 400-800 → publisher net revenues 5-10x.
- Consoles: hardware vendor approval gates (can send back or cancel outright) → far fewer titles, ~7x more profitable net revenues than PC.
- Green-light meetings = eye-candy theater for overworked executives. Better: green-light MINI-PHASE where each discipline presents detailed plans to field experts, composite findings to execs. Microsoft closest: 2-3 months funded preproduction + usability reports; Eidos uses studio heads' gut (20-minute reviews).

## Ch3 (end) + Ch4 Survival Test + Ch5 team anatomy
- Task visibility = Bethke's passion: the TEAM is the most important customer of progress reporting (not execs); Gantt-on-wall updated monthly = failure. Fan-base paradox: a hit brings insatiable feature appetite; the game becomes "their game"; post-release relationship > patch-and-hide.
- Tech pace: games uniquely compete WITH technology (movies' cameras stable 20 yrs); each game builds tools first; engine licensing (Quake/Unreal) to skip that; a completed engine+toolpath BEFORE production or you redo work endlessly. PC chaos: unknown RAM/GPU/OS/CPU (P90 laptop vs P4+GeForce3 ≈ 20x; Moore's law) → minimum requirements EARLY + scalability in graphics/AI + built-in profiling/diagnostics; hardcore games cull old machines aggressively, mass-market hits (Sims, StarCraft, BG) ran on LOW-END systems — part of why they were mass hits. Late surprise example: AMD 3DNow optimization forced 6 weeks before code freeze (publisher signed a 10-product deal). Consoles: fixed hardware + vendor QA → practically bug-free vs PC.
- Sun Tzu's 5 points mapped to game dev: when to fight = preproduction/picking projects; handling superior & inferior forces = scope to financial parameters; same spirit through all ranks = task visibility + team sign-off; prepared waiting = don't hype early; capacity without sovereign interference = experience + publisher non-meddling.
- GAME PROJECT SURVIVAL TEST (38 questions, from McConnell's Software Project Survival Guide; score 3/2/1 per question; take at start/middle/end): Requirements (clear vision statement, team believes it realistic, profit expectation reasonable, core gameplay+UI fleshed out, team thinks it's FUN); Planning (written GDD, written TDD, written art production plan, integrated schedule w/ dependencies, schedule includes E3/GDC/press/installer/autopatcher/console submission, schedule+budget reviewed at every milestone with publisher, features tagged CORE/SECONDARY/TERTIARY for trimming, written QA plan, milestone plan with reviewable deliverables, time for balance/tuning/fun, sick/vacation accounted + devs tasked <100% + leads <75/50%, all leads signed off); Control (single accountable project leader with real authority, right workload, measurable binary milestones, publisher-reviewable milestones, ANONYMOUS reporting channel, written feature-creep plan, change review method, all plans accessible to team, source + BINARY ASSETS under version control, everyone has tools/devkits); Risk (written risks doc + solutions, updated each milestone, a RISKS OFFICER scouting ahead, written subcontractor plan + one owner per subcontractor); Personnel (all expertise present, experienced management, lead programmer capable, enough devs, team gets along, committed to ship). Scoring: subtotal × team-size factor (<9 devs ×1.5, <19 ×1.2). 102+ AAA; 91-101 AA (5-10% overrun); 68-90 A (≤25%); 45-67 B = industry TYPICAL (burnout, turnover, 50-100% overrun); <45 C = cancellation risk ("get serious or be cancelled and save the industry from one more crappy game").
- Ch5 roles: DESIGN (lead designer = director/sculptor of what goes in AND what gets CUT; game mechanics designer — often ex-programmer, balances in Excel simulations; level/mission designers; interactivity writers — dialogue is rhythm/ear, not transcription). CODE ("the ultimate designers are the programmers and artists" — the game IS what they build; designers must convince them; final product = blended vision). McConnell: 50-90% of software projects significantly late; nobody needs a license to write code (hairdressers do) — Bethke advocates licensed lead engineers signing off preproduction→production (Microsoft proto-version: sign-off on developer competence before funding). Lead programmer = chess queen (use her time wisely); technical director = scout lining up dependencies; BioWare/Taldren model: functional assistant leads. Roles: game mechanics programmer ("puts the GAME into the game" — first to see the lightning bolt), 3D graphics (math-heavy, most respected), AI (also writes the scripting languages/designer tools), UI (tricky, underappreciated, maintains the UI library), audio (light; Miles Sound System), TOOLS — id spends >50% of programming on tools (Abrash); BioWare 10+ tools people; "every programmer should be a tools programmer half the time"; tools deserve their own wall Gantt. Mission/level editor = shipping ANOTHER commercial product (UnrealEd). Network: peer-to-peer (bandwidth grows exponentially, cheat-prone — every peer has abusable authority) vs client-server (linear bandwidth, trusted server, needs strict simulation/presentation separation; MMOs = dozens of machines: auth, versions, cheat detection, sim, chat, DB).

## Ch5 (cont.) Art/Audio/Management/QA/Business parts
- Art: art director = quality+theme consistency gatekeeper + dependency scout (most experienced artist with people skills). Concept artist = approval currency (SFC: every ship = B&W sketch → team → Interplay execs → Paramount licensing → Rick Berman, THEN colorize and repeat, THEN model and repeat; LucasArts stricter; Japanese studios concept-artist-centric). 2D/interface designer: "a key team member; be sure you have one, or don't make your game" — NEVER outsource interface art (most changing, most tied to design). Texture phase ≈ 3-4x the modeling time. Key framing (cartoony/extreme motion) vs motion capture (subtle human grace; cost + data cleanup; BioWare has dedicated character riggers). Storyboarder: work out expensive cinematics in boxes+captions first.
- Audio: voice = "probably the coolest element you can add for the money" (George Takei turned SFC tutorials into the most compelling Star Trek moment); only via experienced VO director. Sound effects = ideal outsourcing (only 3+ concurrent-project studios keep a crew busy). Music: $100k for SFC2's 30-piece orchestra; one musician + synth can be strong too.
- Management: "a developer is limited in number of teams not by programmers or artists, but by quality producers" (studio-head consensus). Line producer = absorbs the daily small-task flood (food, printing, builds to publisher/testers) or everyone bleeds efficiency. Associate producer = much responsibility, little authority; updates schedule, strongest game advocate. Studio head/exec producer = plan+execute profitably; id/Epic split business head from project leader.
- QA: no industry-unified best practice; Microsoft most rigorous (and pays/respects QA — rare; most publishers treat QA as low-paid → QA leads are aspiring designers seeking visibility). Publisher QA teams: main, multiplayer (PC-heavy, hard bugs, parallel), FRESH teams (dedicated teams lose the new-player eye quickly — rotate fresh eyes near ship), compatibility (rebuild computers all day), localization (native speakers). Small devs: cross-train line/associate producers as first-line QA + team testing days.
- Beta testing: unpaid fan volunteers; id's Doom/Quake Test = the gold standard (3 maps produced more fun than most finished games). Rule #1: COMMUNICATE with beta testers or they feel betrayed. MMOs need thousands of concurrent testers; skipping rigor = 2-6 months of public post-release beta that burns your early adopters. Beta program manager (usually associate/line producer) = stressful final-months job.
- Business: biz dev gatekeeps pitches pre-green-light. NEVER negotiate a publishing contract without a games-experienced lawyer. Sales: consignment business — retailer can return EVERYTHING (CompUSA orders 200k, returns 160k with price tags on; your 40k sold carried 200k packaging/shipping costs); publishers hide returns for 6-10 quarters then write off; manage sell-in vs SELL-THROUGH. Press relations: ramp buzz to peak AT release (too early = sputter; too little = execs lose faith). E3: press walk in with pre-scheduled appointment lists — small games aren't even on the list; publishers run own events (Interplay's Paramount lot + George Takei event). Marketing manager: don't spread across many titles; campaigns kick off only when ship date is confident.
- HARDCORE FANS = the largest sales factor: word of mouth; one fan sells 6-20 boxes (LAN parties, console living rooms); casual/mass-market gamers ask hardcore friends for recommendations. Diablo/Half-Life/Mario64: "study how NARROW the feature sets really are, and how well and deep these few features are executed."

## Ch5 end + Ch6 Business Context First + Ch7 (start)
- Manual: written 4-6 months pre-release while game in flux → vague, controls-only; strategy guide author = effectively a beta tester (GT3 guide had wrong prices; SFC guide chapters CUT for paper costs after Taldren was slow with info). Manufacturing: gold master → shrink-wrapped on shelves in FIVE DAYS possible (Diablo II, quarter-end); normally 20-30 days; meet the operations manager at 2/3 of schedule to lock deliverable dates. Hardware vendors (NVIDIA etc.) give free test hardware at GDC booths if you're real. Post-release: day after gold master = purest day of career; then patches/forums/support/anti-cheat; MMO "live teams"; ~6 Taldren employees voluntarily moderate forums.
- PROJECT TRIANGLE: On Budget / On Time / High Quality — PICK TWO. "Well-managed projects will be late, cost too much, or be of low quality; less well-managed exhibit two negatives; poorly managed all three." No methodology is a magic potion. The point: identify WHERE YOU'RE FLEXIBLE before the project breaks. Examples: Sims = quality only (5 yrs late+over budget; unique unserved market forgave it; in early stages "there wasn't much to see" for execs); Blizzard/id = quality+budget, time flexible ("when it's done" + joke: Blizzard could ship a million EMPTY StarCraft II boxes on pre-orders; and their job ads require overtime = even they fight time); SFC = budget+time, quality flexible (underdog advantage: exec attention went to Klingon Academy, vision freedom; licensed proven Star Fleet Battles mechanics = tested gameplay foundation; "purity of concept was a godsend"); Klingon Academy = achieved none; Counter-Strike = quality+budget, time wide open (2 years of betas; experienced mod team, 2 main devs; Valve gave design feedback/tech support/financing).
- Four questions on paper: what accomplish? when complete? how much money? who? Ultra-low budget: ≤500-1000 hours/person/year; small game polished (Silver Creek path: 3-4 shippable features > 10 shoddy; "how long to drive feature X to SHIPPING QUALITY is the compelling question") or a mod (CS path). Fixed budget+deadline (Bethke's specialty): walk BACKWARDS from ship date → beta → alpha → production/preproduction budget in man-months; preproduction 15-35% of total time; split features PRIMARY/SECONDARY/TERTIARY and plan to clear dependencies for primary; shift tasks between piles as time allows. KEY PSYCHOLOGY: don't make everything must-do then cross off failures — "people perform badly under the cloud of being failures; set them up to succeed"; winners knock off secondary items voluntarily. AXIOM: all games inherently have primary/secondary/tertiary features; embrace the priority list formally.
- High-profile path: REVERSE DESIGN DOCUMENT — Bethke wrote 27 pages dissecting Diablo (tiles, palette, inventory, UI, manual, box) → epiphany: "Diablo is actually a very simple game with a small set of features." ERIK'S AXIOM 13: "As the complexity of a game increases, its likelihood of commercial success decreases at a GEOMETRICAL rate." Carmack cut portal tech from Quake (still never shipped) = execute features well. Developer productivity varies 10-100x; Carmack learned networking in 2 months and wrote a 2,000-line layer that set the industry standard after a specialist hire failed. Mythical Man-Month: can't add programmers like cantaloupes; past a threshold, NEGATIVE returns (communication complexity); mega-hit teams limit features to what the CURRENT team can produce.
- Ch7: ideas start as "wouldn't it be cool" or a license. Business context ↔ game idea refine EACH OTHER early; late reconciliation = underperforming milestones → painful refunding or cancellation. Effects of a slipped game (7): publisher capital tied, advance stuck, marketing hype wasted (magazine cover 18 months early = worthless), developer reputation tarnished ("poor estimating"), deal NEVER improves (royalty points lost, IP shifts, equity assignment — and any publisher equity stake makes ALL other publishers avoid you), lost other opportunities, team disillusionment/turnover. Taldren counter-example: 5 SFC releases in <2 years = loyal employees ("they know their work will be released and not wasted").
- Ion Storm cautionary tale: Romero + Eidos cash; "design is king" vision interpreted as art-without-process; engine retooling doubled the advance $13M→$26M; press derision, leaked emails, turnover; Dallas closed; even Deus Ex's Austin studio sought a new name to escape the association. "What can be worse than refunding or canceling? SHIPPING IT" (before critical parts complete).

## Ch7 (cont.) Key Design Elements
- Descent to Undermountain disaster: license (AD&D) + hit engine (Descent) assumed to be "a snap"; 6-month/4-dev plan with NO established developer, NO project manager → 3 years, 6x budget, shipped-for-Christmas anyway → Gamespot evisceration ("if you buy DTU after reading this, you get what you deserve"); correct business moves would have been Descent expansion pack from Parallax, or a real AAA budget. "If you're gonna ride the hype machine, you'd better deliver the goods." Quiet releases survive mediocrity better than hype storms. Mega-hits = straightforward gameplay + strong production values; wacky/niche/poor craftsmanship not rewarded.
- Unified Process history: Jacobson at Ericsson 1967 — component-based modeling of telephone switches (blueprints before engineering; demanded by live-upgrade robustness); UML = Jacobson+Booch+Rumbaugh ("three amigos") + IBM/HP/Microsoft. Requirements capture = articulating what the software must satisfy ("be fun", "30 fps"). Method = systematic, repeatable → retain what worked; alternative = ad hoc + luck ("I rather like to make my own luck").
- USE CASES: brainstorm feature radial map (idea center, chunky near, detail far) → identify ACTORS (single-player, multiplayer player, admin, DB server) → use case = oval verb phrase + actor + relationship lines (<<extends>>, <<uses>>); rigor proportional to need. Pac-Man dissected = tiny (4 roles, clone = a weekend for 2-4 people).
- Diablo case study: key concept = USER INTERFACE AS PRIORITY #1 (not story/size/classes/custom looks); left-click attack/open, right-click spell; glass life/mana spheres. In 1995 devs LAUGHED at a "Gauntlet variant" idea as unviable ("no publisher would see it feature-rich enough") — Blizzard North had the courage. Tech: 1997 isometric 2D + 256-color palette (Q-bert-era tech!) BUT 5,000+ frames of animation for 3 protagonists = established tech taken to unprecedented quality; counter-example: unnamed title crippled chasing voxels. Strong art direction = consistent foreboding look.
- Gran Turismo case study: vision "best racing simulator on any platform"; seems to violate tight-features rule (minivans→supercars) but SEAMLESS progression; hidden weapon = CAR MODIFICATION meta-game (= Diablo's inventory/growth dynamic): buy car with starting credits → race → cash → exhaust upgrade (best bang/buck first) → bond with car → back to track; licenses Beginner→International A; always a findable race + earnable cash = forward progress; rally integrated into same core. Players go from zero to discussing gear ratios. His 50+ father bought a PlayStation JUST for GT = true mass-market hit. Physics/graphics/audio excellence mattered but the KEY FEATURES made it.
- Your game: write use cases → group → hunt for activities that are unnecessary/distracting/hardcore-only/hidden → CUT. "Are you sure you are only making ONE game?" Multi-game projects = the years-slipping mistake.
- Rainbow Six vs Counter-Strike: R6 = pro team, full staff, publisher; CS = 2 fans part-time on Half-Life engine; CS CLOBBERED R6 (25-60k simultaneous players). R6's flaw: mission PREPLANNING layer (scripting your AI team like a programmer; every death → back to planning screens; context already provided by campaign+team management; perception/reality gap — "not the game I thought I was purchasing" per BioWare's Ray). CS: multiplayer only, no bots, economy wrapped around fragging (credits → weapons → better play) + sit-out-when-dead tension; thinnest UI. "We are in the profession of delivering FUN, not realism. Realism should only be used to create fun, not detract from it." Clancy source material handicapped R6 into modeling the realistic-but-unfun part.

## Ch7 end + Ch8 Game Design Document
- Marketing can't save a bad game (unlike movies: no "so bad it's good" market at $50, no DVD/cable recovery chain); word-of-mouth dominates. Only 5-15% of buyers ever play a game's multiplayer (excluding MMOs) — CS beat R6 while fishing in that 5-15% pond.
- Elite Force lesson (INTERSECTION vs UNION): Raven + Quake engine + stellar reviews + game-of-the-year press + free expansion → 300k units (~1/3 of Activision's 700k-1M expectation). Theory: genre-crossing must create the UNION of two audiences, not the INTERSECTION. Star Trek fans want starships/diplomacy/clever solutions (phaser = point-and-zap nerd fantasy, "utter disdain for personal martial prowess") — not an FPS; FPS fans got a universe with no visceral personal-combat imagery (vs Star Wars lightsabers → Jedi Knight worked). Successful ST games = adventures + starship games. Ray (BioWare): cross-genre CAN work but each genre's fans must find the other genre's parts ACCESSIBLE at all times — hardest thing to implement.
- Key-design questions to answer in writing (genre/blend? single/multi/both? platform? target market incl. violence/language/sex? major technologies? — each WITH WHY); then visualize, walk, come back, and CUT the non-central features BEFORE writing the 100-page GDD. "All of the great games have a small feature set that is well polished."
- PRODUCTION PLAN = Concept/Vision doc + GDD + Art Design doc + TDD + Project Schedule + Testing Plan + Risk Mitigation Plan. Writing forces thinking to the required quality.
- Proposal reality: pitch docs alone no longer get funding — publishers expect a PLAYABLE PROTOTYPE demonstrating all team talents; developers now shoulder early financing (→ only strong developers make original content). Write the GDD FIRST DRAFT before the proposal (else vague language and guesses).
- GDD truths: Bethke has NEVER seen a finished design document (his own included) — they're maintained through production; measure completeness by HOW WELL THE TEAM WAS LED (confusion? lost work? reworked gameplay?); review/update at every milestone start, and document future changes so devs don't build for cut content. DELEGATE modular GDD sections to the team (controversial): spreads the work AND binds the team ("they can't disengage if it's their ideas") — but give clear topics, style guide, template; visionary keeps executive control.
- Tropico postmortem shock: after a YEAR, half a dozen different visions being implemented simultaneously. Antidote = Section One: articulate the game in a few sentences SO clearly there's no vagueness (Pac-Man and Doom sample paragraphs). Conflict-avoidance warning: leaders who don't cut a member's divergent design direction early create a pissed-off person + confused team later; "tell the truth straight up" (the RTS-hater on an RTS project).
- Set the mood: short opening fiction = the intro movie of the doc (even GT: commentary snippets + racer's journal).
- Section Two Core Gameplay: MAIN GAME VIEW (MUST-DO: every GDD needs a mockup conveying what the game looks like; isometric scale, 3D interior/exterior, view distance), CORE PLAYER ACTIVITY (use cases), CONTROLLER DIAGRAM (inputs→pad/keyboard at a glance), in-game UI items each mocked up.
- Section Three Contextual: shell menus + MENU FLOW MAP; nuts-and-bolts mechanics ("pretend I'm creating a pen-and-paper RPG complete with all details" — spreadsheets/charts; detailing the low level teaches you the high level → loop back and adjust); TUTORIAL philosophy (GT licenses, Mario64 easy levels, BG's safe town of NPC-manuals, SFC:TNG Starfleet Academy frame; goal = get the player playing successfully WITHOUT frustration asap, NOT teach everything); MULTIPLAYER mechanics NOW not later (procrastination → disastrous delays/balance/bugs/outsourced multiplayer — Klingon Academy, RtCW; "being hard is not a good enough reason for putting it off"; players counts, concurrency model — SFC hybrid: hundreds online, battles in 6-player sessions).
- Section Four Talk Story: world backstory (maps! genre-dependent depth; id proud of having none), character backgrounds (characters = cars in GT, units in RTS, SFC:TNG's 3 classes: story characters + ships + recruitable officers), LEVEL/MISSION/AREA design (document colors, textures, lighting, sky, sounds, every trick/trap; campaign flow diagram linear vs open; declare each area's purpose: hub/bonus/UI-as-space like Quake's difficulty selection; designers who can't use 3D CAD tools → narrative + sketches for the level designer).

## Ch8 (end) + Ch9 Technical Design Document (start)
- Cut scenes: storyboard (comic-strip key frames — buy-in tool) + script in standard movie format (VO/OS markers; Black9 briefing-room sample). Section Five assets: DON'T finalize asset lists until technical design is mostly done (tech may cap you at 20 models not 100); categories: sprites/models (spreadsheet with game-specific columns), levels/areas (size/priority/hierarchy), voice (describe actors early, maintain to avoid panic recording), keyframe/mocap SHOT LIST (Black9 sample: 83 moves for ONE character — every state × idle/fire × hit reactions × deaths; "refrain from punctuation, be specific and brief"), sound effects (mentally WALK the levels and listen), music (track blending battle→victory), special effects per genre.
- SFC3 tutorial script sample: instructor voice (Scotty), waits on player action with rotating SARCASTIC comments to hurry + praise on success + prestige points per action — tutorial as in-world character with personality.
- Black9 audio bid anatomy (real vendor bid, "Tommy" = Tallarico): music $1,000/minute (discounted from $1200-1500 for volume), 53 min ≈ $53k (3 worlds × search/ambient + chase/battle + 5-second stings; 1:30 loops instead of 2-3 min = trick to stretch budget); sound design $30k for ~1000 sfx (100 common + 50/level × 16 + 160 cinematic + 10 menu; ambient loops "the player will hear these MORE than the music!"); VO $22k (35 characters / 15 non-SAG actors @ $750 buyout avg, 3 studio days @ $1k, casting $1k, edit/master $5k, 10% contingency for callbacks). Degradation options to $81k with explicit quality warnings ("A/AAA needs the 100K; B title 80K; anything less = C title blues"). Weapons/ammo table sample: cost/range/damage/ROF/magazine/faction/threat/mission-first-available + tweak notes.
- PRACTICE ADVICE: write a full game design document for an EXISTING successful game before designing your own (every profession practices first).
- Ch9: OOD assumed (C++ bias; Java = low-perf cross-platform; C = team choice). TDD = blueprint: WHAT + HOW, broader/less detailed than a software architecture plan; synthesizes requirements, software design, testing plan, + project-manager data (roles, dependencies, time estimates). JAY LEE STORY: spent 2 months writing ONLY header files (interfaces for every class of an MMO casino game) — team skeptical ("shouldn't our best programmer write code?") — then 3 junior devs fleshed out the implementation in 3 months: "the fastest any of us saw software come together." Interface-first architecture works.

## Ch9 (cont.)
- Publishers now demand TDDs but few can review them → invisible deliverable; execs want eye candy instead → devs pressured to skip technical design and play catch-up all project. Bug-fix cost: ~50x more expensive at end of implementation vs design stage. Make technical design work VISIBLE and reviewed.
- Weak process = wasted time at the END of the project (cancellation-grade holes); "all games taking 30-60 months are at houses with poor process → poor preproduction." Why game companies resist process: software industry is bad at it generally + creativity-as-excuse ("sacred") + Moore's-law scope growth means a manager's hands-on experience from 5 years ago is 8x too small — "a great source of subtle evil in the game industry."
- Unified Process core workflows: REQUIREMENTS → ANALYSIS → DESIGN → implementation → test (most studios only know the last three); phases per workflow: inception/elaboration/construction/transition; iterative (late inventory-system redesign walks the whole loop again). Naming the activity you're in = awareness = better output.
- TDD written in preproduction, staggered after GDD; mini-technical-design stage before ANY mid-production change; designs are not stone tablets.
- Requirements capture: EVERY expectation (60fps, one CD, ≤80 programmer-months, 3D sound, 10k-poly characters); cast the net wide, NO culling/prioritizing yet (premature analysis bogs down + decides on partial info). Easiest source = the GDD. Use case diagrams per shell screen + menu flow diagram (required); spend most analysis time on the MAIN DISPLAY (mock it up, hunt every interaction, whiteboard first, then factor common functionality, then adorn with non-interaction requirements like frame rate). DON'T analyze into implementation during capture. SFC3 officer-menu example: complete use case doc with display elements, skill-rank color ladder (Basic→Legendary), transfer in/out mechanics incl. K-constant for trade-in value, ensign-vanishing anti-exploit, auto-assign algorithm — level of detail a dev can code from.
- UML tenet: never create documents for documentation's sake; 9 diagrams exist, use judgment ("you might make a bureaucrat proud" but never ship). Reverse engineering with use cases = the tool for inheriting codebases/sequels (Ken Yeast story: diagrammed matching system → fixed subtle bugs by "seeing" expectations). You'll NEVER find all use cases in preproduction; fold new ones in as found.
- Nonobvious requirements: design (user extensibility, existing code base), interface (OpenGL vs DirectX portability), implementation (billing-grade transactions; platform), performance (frame rate, latency tolerance).
- Requirements analysis = analysis model: player language → developer language; external view → internal view; first pass at architecture WITHOUT final class diagrams (committing to the first use case produces a system that only answers that use case); depth proportional to complexity (MMO client-server = yes; two-button menu = the use case diagram IS the final design).
- Class diagram = workhorse of technical design: classes + relationships ("is a" arrow to parent, "has a" plain line with cardinalities 1/*/6; compile-time dependency = third cousin, don't draw them all); notes/adornments for performance requirements. Object diagram (instances: Goblin:Monster), package diagram (file-folder organization once ~a dozen classes blur), activity diagram (= polished flow chart), sequence diagram (client-server message flows), component diagram (modules/DLLs/databases), deployment diagram (MMOs only; otherwise "suitable only for impressing Dilbert's boss").
- BUILD TIMES as productivity evil: 5-15s = no broken concentration; 1-2 min = thinking time; 5+ min = serious leak; 20+ min = people wander off and 2 hours vanish. Header-file touches cascade. SFC code 4 years old: 30+ min builds for minor architectural changes — "we had no idea the game would succeed enough to merit working with the same code four years later"; full rewrite unaffordable → INCREMENTAL REFACTORING (3D engine → DLL, refactored multiplayer layers, wrapped the bad inherited Quill UI engine in "a safe and sane coding condom"). Fowler et al. Refactoring recommended.
- INSULATION / Interface-Impl: public interface class holding a private implementation class → implementation changes recompile nothing else. Verify every #include is needed; don't copy include lists "like a huge fishing net."
