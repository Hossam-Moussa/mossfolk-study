# State Design Pattern في Unreal Engine (fAYgB3Pyr58، ~9 دقايق) — نوتس مذاكرة

> ملحوظة: العنوان والمدة مش متأكدين منهم، المدة تقديرية من الترانسكريبت. الترجمة الآلية فيها أخطاء: "NCAA" غالبًا = C++، و"Spitzer class" غالبًا = Character/Pawn class.

---

## 1. التعريف: الـ State Pattern في جملة (★★★)

- **State design pattern** = **behavioral design pattern** بيخلي الـ object **يغيّر سلوكه لما حالته الداخلية (internal state) تتغير**. يعني الكلاس نفسه مش بيتغير، اللي بيتغير هو **إزاي بيتصرف** حسب الحالة الحالية.
- الفكرة الأساسية: الكود بيسأل "أنا فين دلوقتي؟" وبيتصرف على هذا الأساس، بدل ما يكون فيه `if` ضخمة متلغبطة.
- **الباترن ورا الفكرة:** كل حالة بتتعامل كوحدة سلوك مستقلة، والانتقال بينها بيكون بشروط واضحة. ده بيخلي الإضافة أسهل (حالة جديدة = وحدة جديدة وانتقالات) بدل ما تعدل كل حاجة في كل مكان.

---

## 2. الصورة الكاملة: الـ State Machine موجودة في كل طبقات الـ Unreal

المحاضر بيقول إن نفس الفكرة بتتكرر في أربع طبقات مختلفة من المحرك. ده مهم عشان المصمم يفهم إن الـ pattern مش حاجة "برمجية" بس.

1. **Enums كـ state** (على مستوى البيانات).
2. **Animation Blueprint state machine** (على مستوى العرض/الحركة).
3. **Character Movement** (على مستوى الفيزياء والحركة).
4. **AI Behavior Tree / AI states** (على مستوى الذكاء الاصطناعي).

---

## 3. الـ Enums كـ State Machine بسيطة (★★★)

- **المثال الأول: Movement Mode** في الـ **Character Movement Component**: الشخصية بتنتقل بين **Walking → Falling → Swimming → Flying**. كل قيمة enum = حالة، والمحرك بيغير سلوك الشخصية كلها حسبها (الجاذبية، التحكم في الهوا، الحركة في الميه...).
- **المثال التاني: Collision في الـ Capsule Component**: إعدادات التصادم كمان enum، وتغييرها = تغيير الحالة الفيزيائية للكائن.
- **القاعدة اللي بيقولها:** "كل حاجة بتشوفها كـ enum بتعتبرها تغيير حالة للكلاس ده". ده أساس فهم إن الـ state مش لازم يكون معقد عشان يكون state.
- **الباترن ورا التاكتيك:** أبسط تطبيق للـ state pattern هو **enum + switch**. ابدأ بيه قبل ما تبني كلاسات لكل حالة، ولو الحالات قليلة وبسيطة، الـ enum أكفأ وأوضح.
- **تحفظ مهم (ملاحظة مني على الفيديو):** المحاضر بيعمم إن "أي enum = state machine". ده مش دقيق: الـ enum اللي مفيهوش **انتقالات** (transitions) وشروط بتربطها ببعض هو مجرد **نوع بيانات (type)**، مش state machine كاملة. الفرق بيبان لما تسأل: مين بيغير الحالة؟ وإيه الشرط؟

---

## 4. Animation Blueprint كـ State Machine (★★★)

- **المثال: الـ Third Person Template**: الشخصية بتنتقل بين حالات زي **Idle، Jogging، Sprinting، Death، Climb/Clamping**. كل حالة ليها animation مختلفة، والانتقال بينها بيتحكم فيه input أو قيمة من الـ gameplay.
- **أمثلة الانتقالات بالاسم:**
  - **Idle → Sprint** لما تضغط **Shift** على الكيبورد.
  - **أي حالة → Death** لما الشخصية تموت، فتتشغّل **death animation** (حالة Death بتاخد الأولوية).
  - **Jumping → Falling → Land** كسلسلة حالات داخل الـ **AnimGraph**.
- **Demo الـ Locomotion (Default Locomotion):** الحالة **Idle** بتنتقل لـ **Walk Forward** بشرط: **هل الشخصية بتتحرك؟** والتحقق بيتم بـ**طول متجه السرعة (velocity vector length) أكبر من صفر**. لو أيوه → حالة الحركة، لو لأ → ارجع لـ Idle.
- **الباترن ورا التاكتيك:** الانتقال بيعتمد على **قيمة مراقبة (observable value)** مش على الـ input المباشر. السرعة هي اللي بتقول الحالة، مش الزرار. ده بيفصل **"الحالة"** عن **"سبب الحالة"**، وبيخلي الأنيميشن يتصرف صح حتى لو الحركة جت من مصدر تاني (AI مثلًا).

---

## 5. الـ AI Behavior Tree كـ Finite State Machine (★★★)

- **المحاضر بيسمي الـ Behavior Tree "finite state machine"** وبيوريك إزاي الـ AI بيغير حالته سلوكيًا.
- **مثال الـ AI الأساسي:**
  - **Patrol** (دورية) ← الحالة الافتراضية.
  - لو **عنده line of sight** على اللاعب → **Rotate** ناحيته و**Chase** (مطاردة).
  - لو **فقد الرؤية** → رجع لـ **Patrol**.
- **مثال الـ Enemy المعقد (بيوضح الأولويات):**
  - لو **سمع صوت (hearing noise)** → يروح لمكان الصوت (Move to noise location).
  - لو **شاف اللاعب** → يتبع حالة المطاردة و**يتجاهل الحالتين التانيين** (يعني الرؤية بتعمل **interrupt** على الحالات الأقل أولوية).
- **الباترن ورا التاكتيك: ترتيب الأولويات.** الـ AI مش بيعمل كل حاجة مرة واحدة؛ فيه **حالة نشطة واحدة** وإدراك (sensing) بيقدر يقاطعها حسب الأولوية: الرؤية > الصوت > الدورية. ده بيخلي السلوك قابل للتوقع وقابل للتصميم.

---

## 6. الـ Weapon Type Enum: نفس الحالة، سلوكيات متعددة (★★)

- **المثال العملي:** تعمل **enum** اسمه **E_WeaponType** فيه: **Pistol، Shotgun، Rifle**.
- بتعمل **variable** من النوع ده، وبتستخدم **Switch on Enum**: لو Pistol → سلوك، لو Shotgun → سلوك تاني، لو Rifle → سلوك تالت.
- **مثال الـ Pickup:** لما تلقط ذخيرة، الكمية بتتحدد حسب نوع السلاح الحالي (عدد رصاص pistol مختلف عن shotgun...).
- **الباترن ورا التاكتيك:** **حالة واحدة (نوع السلاح) بتتقري من أنظمة كتير** (الإطلاق، الـ pickup، الأنيميشن، الـ UI). ده بيخلي التعديل في مكان واحد (الـ enum) بيأثر على كل الأنظمة المتصلة بيه، وده أساس الـ data-driven design.

---

## 7. الخلاصة: الـ Pattern بيتكرر في كل مكان (★★)

- الكلام الختامي: **enum = state machine، Animation Blueprint = state machine، Behavior Tree = FSM**. المحرك بيقدم دي كأدوات جاهزة، والمصمم بيختار مستوى التعقيد المناسب:
  - Enum للحالات البسيطة.
  - Animation state machine للحركة والأنيميشن.
  - Behavior tree/FSM للـ AI.

---

## 8. الباقي برمجة — متجاهل

- تفاصيل الـ Blueprint nodes (`Set Movement Mode`، `Switch on Enum`، `Get Velocity`، `Vector Length`) والـ wiring والـ C++ اللي وراه: متجاهلة حسب قاعدة الاستوديو.
- إعلان كورس Udemy في آخر الفيديو: متجاهل (مش محتوى تصميمي).

---

**للاستوديو:**

- **Bot Tester كـ FSM صريحة (ينفع لأي لعبة):** عرّف حالات الـ bot زي `Scanning ← ChoosingAction ← Executing ← Waiting ← Evaluating ← GameOver`، وكل انتقال يكون بشرط مقروء وقابل للقياس، مثلًا "الـ physics وقفت" = سرعة كل الأجسام تحت حد معين، أو "الـ UI ظهر" = الـ element موجود في الـ scene. ده بيخلي `bot_difficulty` يتحكم في **شروط الانتقال** أو **زمن الانتظار**، مش في كود متلغبط جوا كل حالة. (مثال على اللعبة الحالية Mossfolk: الـ bot بيستنى الكرات توقف قبل ما يقرر الخطوة الجاية، والصعوبة بتتحكم في حد السرعة وزمن الـ Settling.)

- **المخلوقات والوحدات كـ enum + transitions للـ merge أو الترقية:** كل مستوى أو حجم حالة، والانتقال للأعلى بيحصل بشرط واضح، زي "اتنين من نفس المستوى اتلمسوا". ده الـ state pattern بالظبط للـ merge والترقيات، وينفع في أي لعبة فيها evolve chain أو upgrade chain. (مثال على Mossfolk: 9 أحجام، كل حجم حالة، والانتقال للأكبر بيحصل بشرط اتنين من نفس الحجم اتلمسوا.)

- **Enum واحد بسلوكيات مختلفة (Weapon Type pattern):** لو عندك أنواع عناصر ليها spawn rules وmerge rules وscoring مختلفة، خليها enum واحد، والـ switch هو اللي يحدد السلوك، بدل ما تعمل class لكل نوع. (مثال على Mossfolk من ليفل 2501: الـ mossy shells بتتقشر، والـ stones تقيلة، والـ rot بيتحلل بعد زمن.)

- **Mini-games والمسابقات كـ state machine مستقلة:** كل مسابقة ليها حالات زي `Intro ← Playing ← Scoring ← Result`. وأي ad أو popup أو حدث monetization يتحط بس في حالة `Result` أو بين الجولات، عشان ما يقاطعش `Playing`. (زي الـ rival contests في Mossfolk: الإعلان مكانه بعد النتيجة، مش وسط المنافسة.)

- **تحذير من Overgeneralization (استنتاج شخصي، مش من الفيديو):** مش كل enum محتاج state machine كاملة. لو قيمة الـ enum مفيهاش انتقالات واضحة، سيبها كـ type بسيط ومتعقدش الكود. قبل أي state جديدة اسأل: **مين بيغيرها؟ وإيه الشرط؟** لو مفيش إجابة واضحة لأي منهم، الحالة دي غالبًا مش محتاجة تتعمل.

- **Audit سريع للـ QA:** لكل لعبة في الـ pipeline، اكتب جدول انتقالات (من ← لـ ← الشرط) لكل حالة. أي حالة مفيهاش مدخل أو مخرج تعتبر bug أو dead state محتمل، ومراجعة الجدول قبل الـ soft launch بتوفر وقت كبير في الـ debugging بعدين.
