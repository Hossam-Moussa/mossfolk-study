# Command Design Pattern في Unreal (lFVRpL8EvSI، ~21 دقيقة) ★ — نوتس مذاكرة

الفيديو كله برمجة (Unreal C++/Blueprint: subsystem Singleton، كلاسات Command، الـ cast، الـ widget). **الباقي برمجة، متجاهل.** الترانسكريبت أوتو-جنريتد ومشوّش في أسماء كتير. اللي يهم التصميم والعملية:

- **الباترن نفسه:** الـ Command يغلّف الفعل كـ object (`execute`)، وتمرر له الـ target (الوحدة المختارة). الفكرة التصميمية إن «اختار حاجة، وبعدين اديها أمر» بقى نفس الفلو في كل النوعات. المصدر ذكر أمثلة بالاسم: **turn-based tactics** (شبه Gears Tactics بحسب الترانسكريبت المشوّش)، و**XCOM** (UIs متداخلة، وتقدر **تعمل undo** لأمر الوحدة)، و**RTS** («بيتستخدم بكثافة»)، و**card games** (تختار كارت وتمرره كأمر، وبعدها تختار الـ target) ★. المتحدث نفسه بيقول إنه مش لاعب RTS وخبرته في التاكتيكس محدودة، فالأمثلة دي لتوضيح الفكرة بس.
- **الفوايد المذكورة** (من refactor.guru وgameprogrammingpatterns.com): single responsibility، وopen/closed (تضيف أمر جديد من غير ما تلمس القديم)، وundo/redo (`undo` أو `stop`، زي إيقاف وحدة عن بناء أو عن حركة). الباترن ورا ده: الأمر الواحد يتتبع ويتلغى ويتبدل مستقل عن اللي بينفذه، وده بيبسّط تغيير الـ input والتوسع.
- **الديمو:** كاميرا + 3 أزرار على وحدات survivor (Build Barricade، Defend the Base، Kill Zombies). لو مفيش وحدة مختارة تظهر رسالة «no unit has been selected»، ولما تختار وحدة الأمر ينفذ ★. دي مجرد log، مفيش لعب حقيقي. الدرس الوحيد التصميمي: **حالة «مفيش اختيار» لازم يبقى لها feedback صريح.**
- **للاستوديو:**
- **Undo / Reversibility:** أي فعل فيه فيزياء أو حالة مش قابلة للعكس بسهولة محتاج قرار تصميم منفصل قبل ما نكتب الـ undo. الاختيارات: حفظ snapshot، أو يبقى ميزة اختيارية، أو مكافأة إعلان (rewarded ad). مش مطلوب تنفيذه دلوقتي. (مثال على اللعبة الحالية Mossfolk: undo آخر إسقاطة، لأن الفيزياء مش قابلة للعكس بسهولة.)
- **Replay / تيستر-بوت:** لو كل action اتسجل ككوماند (بيانات الموضع والحجم أو الاختيار)، يبقى عندنا replay وتيستر-بوت بيلعب الليفلات تلقائيًا ويكشف الـ softlocks وعدم توازن الصعوبة. الشرط: الـ simulation لازم تكون deterministic، وده مش مضمون في أي محرك افتراضيًا (fixed timestep، seeded random، ترتيب ثابت للتحديثات). لازم نتأكد بتجربة قبل ما نبني عليه. (مثال على Mossfolk: تسجيل كل إسقاطة كموضع + حجم، والتحقق إن فيزياء Unity بتعيد نفس النتيجة.)
- **Multi-step commands / Boosters:** لو فيه فعل على مرحلتين زي "اختار البوستر ثم الـ target" (زي الكروت في أي card game)، الـ selection بيتعامل كـ state مؤقت، ولازم يتلغى لو المستخدم ألغى الاختيار، والـ command ميتنفذش غير لما الاتنين يكتملوا. (مثال على Mossfolk: لو اتضافت البوسترات في الـ side quests، المستخدم يختار البوستر الأول وبعدين الـ target.)
